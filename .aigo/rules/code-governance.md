# 代码治理规则

## 范围与证据

- 先确认需求、所有权和影响边界，再修改代码。歧义会改变行为、数据安全或交付范围
  时才提问。
- 只修改当前任务直接相关的文件。用户已有改动必须保留；发生重叠时先读差异，不能
  用重置、覆盖或全文件格式化清除。
- 以源码、配置、锁文件、测试和日志为依据。旧计划、历史审计与注释可能过期，不能
  单独证明当前行为。
- 新依赖、生产配置、数据库破坏性迁移、真实外部服务和付费资源不属于普通实现步骤，
  必须先确认。

## 所有权与分层

- 先定位拥有该行为的 bounded context，再从其 `public`、`composition`、用例与测试
  追踪调用链。
- 领域规则只存在一份。不要在 route、React 组件、Electron IPC 或适配器中复制判断。
- 跨上下文调用只经过目标上下文的稳定 `public.py` 或 `public.ts`；禁止直接导入其他
  上下文的 domain、application 或 infrastructure 私有路径。
- 迁移完成后删除由本次改动产生的旧引用，不新增兼容 re-export、facade、双写或第二套
  请求路径。原本存在且与任务无关的死代码不顺手清理。
- 目录表达稳定边界，不按文件行数拆分；没有独立职责、只增加跳转的包装层不应创建。

## 完成条件

- 行为、测试与文档保持一致；自己的改动没有废弃引用或未跟踪生成物。
- 验证范围与风险匹配，失败原因可复现。连续三次同类失败后停止重试并重新判断根因。
- 交付只陈述实际改动和已运行检查，不把计划、推断或未执行命令写成完成事实。
