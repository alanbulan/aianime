## 一、严重

### S1. Hermes 子进程 stderr 管道无消费者 —— 管道写满后死锁
- `src/ai_anime/modules/ai_assistant/infrastructure/hermes/hermes_sdk.py:404`
- `stderr=asyncio.subprocess.PIPE` 但全文件无任何读取 stderr 的代码；`close()` 只关 stdin + terminate。
- hermes 为常驻 Node CLI，stderr 写满 OS 缓冲（4–64KB）后子进程阻塞 → stdout 停止产出 ACP 帧 → 会话初始化/流式回合超时（STREAM_READ_TIMEOUT 300s）被强杀。**随会话变长、日志变多，触发概率递增**。这可能是"助手等待卡住"类问题的另一个未修根因。
- 修复：spawn 后 `create_task` 循环 drain stderr 写日志，或重定向到文件。
- 置信度：高（已复检确认）

## 二、中等

### 后端（src/）

**M1. 风格预览 mkdtemp 临时目录永不清理（磁盘泄漏）**
- `asset_world/infrastructure/style_generation.py:62` 创建 `style_preview_*` 临时目录；上游 `application/styles.py:354-364` 只 `read_bytes()`，无 rmtree。每次生成风格参考图残留 1–3MB。
- 修复：读字节后 `shutil.rmtree(output_dir, ignore_errors=True)`，最好放 try/finally。
- 置信度：高（已复检确认）

**M2. 聊天 WebSocket 会话循环对畸形消息不设防**
- `api/routes/ai_assistant/session.py:67,69,139,174`：`raw.get("type")` / 三处 `model_validate` 都在 try 之外。客户端发一条类型错误的 `chat.message` → ValidationError 传播 → 连接异常断开、无错误反馈。
- 修复：循环体包 try，失败时回 error 事件 + continue。
- 置信度：高

**M3. 画布保存在事件循环上做文件锁忙等 + 同步 IO**
- `creative_canvas/infrastructure/canvas_lock.py:44-56`（`time.sleep(0.02)` 自旋至 3s）→ `canvas_store.py:247` → `api/routes/creative_canvas/documents.py:198-207`（async 路由直接同步调用）。大画布保存/锁竞争期间**整个 sidecar 停摆**（含聊天心跳）。
- 修复：`await asyncio.to_thread(commands().save, ...)`。
- 置信度：高

**M4. 任务编排"已开始"阶段异常留下永久 running 僵尸任务**
- `task_execution/application/project_task_execution.py:328-345` / `infrastructure/inline_backend.py:256-273`：`runner()` 之外的异常（如首个 `update_progress` 碰上 SQLite busy）逃逸后无人把任务标 failed；僵尸行还会让 `reserve_task_for_project` 去重持续命中 → 后续同类型任务被拒（"重复调用"表象复发面）。
- 修复：`_on_background_task_done` 拿到异常时对该 run_task_id 补 `fail_task_for_project`。
- 置信度：中

**M5. SQLiteStore._ensure_db 检查-连接竞态（连接+线程泄漏）**
- `shared/infrastructure/project_sqlite_core.py:111-133`：`_lease` 是计数器不是锁，首次并发调用会 double-connect，先建的 aiosqlite 连接（各持一线程）永久泄漏。修复：加 `asyncio.Lock`。
- 置信度：中

**M6. HermesPool reaper 持全局锁做慢 IO；长回合可能被 idle-kill**
- `hermes_pool.py:513-527, 479-490`：reaper 在 `self._lock` 内逐个 close（3s/个 + 网络调用），阻塞所有用户发消息；`last_used` 仅在 get 时刷新，超长回合中 worker 可能被 evict → 回合静默截断。
- 置信度：中

### 桌面（desktop/）

**M7. videoTaskRoutes 无界增长 + sticky 路由永不过期**
- `commercial-model-proxy.ts:98,409,245`：每条成功视频任务写入 sticky 路由快照（含 apiKey/baseUrl），无 TTL、无容量上限；用户删除/更换 BYOK provider 后，既有任务轮询永远路由到已废弃 provider 且无 fallback，直到重启。**注意 sticky 快照持有 apiKey，长期驻留内存也增加敏感面。**
- 置信度：高（已复检确认）

**M8. LocalBackend stop→start 竞态可产生孤儿 sidecar 进程**
- `desktop/src/backend.ts:146-149,156-180`：旧子进程 exit 回调无条件 `this.child = null`，会把新子进程引用抹掉；后续 stop 失效 → 孤儿进程。当前 main.ts 无重启路径，暴露面有限，但属可复用类的确定性缺陷。
- 置信度：高

**M9. synchronizeModelAccess 无并发互斥**
- `commercial-ipc.ts:622-630` 被 8+ 处 handler 调用：proxy 路由（同步替换）与 sidecar 能力配置（HTTP POST）两步可能乱序 → 路由表与后端能力错配。修复：handler 层串行化或加 in-flight promise 合并。
- 置信度：中高

### 前端（frontend/）

## 新发现（复检引入检查）

### N1.【中等】`isRetryableRequestFailure` 判定过宽，吞掉云端会话错误的路由回退
- `desktop/src/commercial-model-proxy.ts:1590-1604`（新增）+ 调用点 `:359-366`
- 4xx 不可重试的意图只针对 `prepareBodyForRoute` 的客户端校验错误（body 相同必失败），但 `modelRequest` 内部也会抛出携带 4xx 状态的异常：
  - `commercial-api-client.ts:1183` "云端账户尚未登录"（401）
  - `commercial-api-client.ts:841` "当前设备尚未激活"（403）
- 这些错误**特定于 cloud 路由**，旧逻辑会重试后 fallback 到同角色的下一条路由（如 BYOK）；新逻辑直接抛出、不再回退。场景：角色配置了 cloud 优先 + BYOK 备选，云端会话失效时原先可自动降级 BYOK，现在直接失败。
- 建议：只把"请求体准备阶段"的错误标记为不可重试（如 `prepareBodyForRoute` 外单独 try/catch 打标），而非按状态码范围一刀切。
- 置信度：高（代码路径确认）；实际影响取决于 cloud+BYOK 混合路由配置下会话失效的发生频率。
