# 创作点修复与一一点一点七十八发布记录

## 时间、环境与原因

北京时间二〇二六年九月十九日，用户反馈正式版 `1.1.77` 仍显示旧积分，并授权检查
桌面端残余问题、推送两个远端及执行三平台构建发布。首先将已有源码提交 `8ffaa216`
推送到远端；本轮追加完整回归和发布版本 `1.1.78`，不覆盖 `1.1.77` 的安装包。
本地环境为 Linux，三平台原生构建与制品验证交由现有发布工作流执行。

## 换算与残余修复

新口径为一元十创作点，每创作点一亿基础账务单位。截图中的两处值应为：

| 场景 | 原始整数 | 旧显示 | 新显示 |
| --- | ---: | ---: | ---: |
| 顶栏可用余额 | `991110000000` | 991,110 积分 | 9,911.1 创作点 |
| 图片预计费用及预算上限 | `217500000` | 217.5 积分 | 2.175 创作点 |

检查发现预算确认与账单测试仍断言旧精度，发布工作流会因此失败；修正断言，增加截图
对应余额和图片预算测试，并覆盖最小金额及安全上限。浏览器测试实际显示创作点，
点击确认仍只提交请求标识与决策，主进程解析仍保留原始授权整数，不重复缩放金额。
修正一条残留金额格式错误提示为“创作点金额格式无效，请刷新报价后重试”。

管理端新增的换算描述字段不属于桌面配额启动接口。核对桌面实际消费合同后，保留
字段严格校验，未用忽略未知字段的方式掩盖合同漂移。余额、预算、账单、使用量和
中英文单位已采用相同精度。旧安装包需要更新并完整重启才能生效。

版本、发布说明和版本回退值同步为 `1.1.78`。提交后推送 Gitee 与 GitHub 的 `master`，
核对同一提交，再推送中文注释标签 `v1.1.78` 触发既有 `build-desktop.yml`。
该工作流分别在原生 Windows、Intel Mac、Apple Silicon Mac 运行合同测试、打包、
资源与更新验证，再统一校验并发布到云端。实际运行编号及最终结果在后续记录追加。

此提交时尚未把 Actions 结果或人工安装验收写成成功。Linux 本地测试不能证明三端
实际人工安装、登录、付费生成和自动升级体验。失败时保留日志并修复后重新推送，
已经公开发布的相同版本制品不得覆盖。显示改动未改变价格、原始金额或资产购买力；
如发现显示问题优先发布新版本修复，不对数据库金额再次缩放。

## 用户追加启动报错的实际复核

用户在构建期间报告 `quota response fields must be exactly account, buckets, spendableUnits`。
用历史提交 `8efefb41` 之前的主进程解析器读取当前云端响应，逐字复现此报错：旧字段表
缺少当前必需的 `assetVersion`。标签 `1.1.73` 起已包含该字段，不能仅凭报错认定用户
机器实际安装的是哪个版本；仍需结合正在运行的主进程及安装来源判断。

重新只读导出已存在的租户十四个人账户及当前模型目录，经过正式 Gateway 配额投影、
当前已编译主进程启动解析、桌面与界面解析器及 Python 能力接口：十个当前可见模型通过，
可用余额及退款冻结原值保持。没有新增登录、设备激活、报价、模型请求或费用。
当前 `1.1.78` 启动解析要求四字段，不会出现上述仅列三字段的旧规则错误。

带实际云端证据再次执行：桌面三百一十五项通过、五项跳过；真实界面启动和余额组件
十六项通过、零跳过；Python 合同十六项通过、零跳过。此前两个缺少现场资料而跳过的
相关验证已补齐；剩余桌面跳过项为宿主及独立目录资料条件。不忽略额外字段，也不删除
服务端资产版本字段来迁就旧程序。安装新版本后必须完整退出并重启桌面主进程。
